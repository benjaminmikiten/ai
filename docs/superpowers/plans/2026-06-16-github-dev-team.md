# GitHub Dev Team Skills — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
> **ALSO REQUIRED:** Before writing any skill file, invoke `superpowers:writing-skills` to load the skill-writing guidelines.

**Goal:** Build 6 composable Claude Code skills that simulate a GitHub-native software development team (PO, Tech Lead, Engineer, Reviewer, Orchestrator, Setup).

**Architecture:** Each skill is a standalone `SKILL.md` in `~/.agents/skills/<name>/`, symlinked from `~/.claude/skills/<name>`. Skills share state exclusively via GitHub (issue labels, comments, branch commits, PR review state). A per-repo `docs/agents/dev-workflow.md` reference doc (installed via `/dev-team-setup`) defines label vocabulary and naming conventions for each target repo.

**Tech Stack:** `gh` CLI, `git`, Claude Code skill markdown, existing skills: `to-prd`, `to-issues`, `review`

## Global Constraints

- Skills live at `~/.agents/skills/<name>/SKILL.md`
- Symlinks: `~/.claude/skills/<name> -> ../../.agents/skills/<name>`
- Every agent-posted GitHub comment must start with `> *This was generated by AI during the dev team workflow.*`
- Each skill reads `docs/agents/dev-workflow.md` from the CWD (target repo) before acting
- All GitHub I/O uses `gh` CLI; all git operations use standard `git` commands
- State machine labels: `needs-po` → `prd-pending` → `prd-approved` → `adr-pending` → `adr-approved` → `in-progress` → `needs-review` → `done`
- The review skill is named `/dev-review` (not `/review`) to avoid collision with the existing `review` skill already installed in `~/.agents/skills/review/`
- Child PRs target the feature branch (not main); they are merged into the feature branch as each child is approved

## Approval Heuristic

When a skill checks for your approval, it reads the comments posted **after** the last agent comment on the issue.

**Revision requested** — the comment contains change requests, correction language ("but", "instead", "should be", "needs to", "fix", "update", "change X to Y"), or any imperative directed at the agent. Extract the specific changes and pass them as context.

# Product Owner

Write (or revise) a PRD for a GitHub issue, commit it to the feature branch, and post it as a comment for your review.

## Invocation

```
/po #<issue-number>
```

## Process

### 1. Load workflow config

Read `docs/agents/dev-workflow.md`. Extract label strings and naming conventions. If the file doesn't exist, tell the user to run `/dev-team-setup` first and halt.

### 2. Read the issue

```bash
gh issue view <N> --json number,title,body,labels,comments
```

Extract:
- Issue title and body (the feature request)
- Current labels
- All comments, in order

### 3. Determine mode

**Revision mode** — if the issue has the `prd-pending` label:
1. Find the last agent comment (starts with `> *This was generated by AI during the dev team workflow.*`).
2. Read all comments posted after it. Apply the approval heuristic from `dev-workflow.md`.
3. If **approved**: transition label `prd-pending` → `prd-approved` and halt with message: "PRD is approved. Run `/tech-lead #<N>` (or `/dev-cycle #<N>`) to continue."
4. If **revision requested**: extract the specific changes and continue to Step 4 with the existing PRD as a starting point.
5. If **no response**: halt with message: "Waiting for your review of the PRD on issue #<N>. Approve or request changes there, then re-run `/po #<N>` or `/dev-cycle #<N>`."

**Fresh mode** — no `prd-pending` label: proceed to Step 4 with no existing PRD.

### 4. Derive branch name and slug

```
slug = issue title → lowercase → replace /[^a-z0-9]+/ with "-" → truncate at 40 chars → strip leading/trailing hyphens
branch = "feature/<N>-<slug>"
prd_path = "docs/prd/<N>-<slug>.md"
```

### 5. Draft the PRD

Using the issue body and any existing PRD (in revision mode) as input, write a PRD following this template:

```markdown
# PRD: <issue title>

**Issue:** #<N>
**Date:** <today>

## Problem Statement

[The problem the user is facing, from the user's perspective. 2-4 sentences.]

## Solution

[The proposed solution. 2-4 sentences.]

## User Stories

[Numbered list. Each in the format: "As a <actor>, I want <feature>, so that <benefit>." Include at minimum 5 stories covering the core use cases.]

## Implementation Decisions

[Key technical decisions, interfaces, and constraints that came out of the issue discussion. Focus on WHAT, not HOW. Omit file paths.]

## Out of Scope

[Explicit list of things not covered by this issue.]
```

In revision mode: apply only the requested changes. Preserve all content that wasn't flagged.

### 6. Commit to branch

```bash
# Create branch if it doesn't exist
git checkout -b <branch> 2>/dev/null || git checkout <branch>

mkdir -p docs/prd
# Write PRD content to docs/prd/<N>-<slug>.md

git add docs/prd/<N>-<slug>.md
git commit -m "docs(prd): add PRD for issue #<N>"
```

### 7. Post to GitHub

Post the full PRD content as an issue comment:

```bash
gh issue comment <N> --body "$(cat <<'EOF'
> *This was generated by AI during the dev team workflow.*

## PRD: <issue title>

[full PRD content here]

---
**Review this PRD and reply with your feedback or approval. Then re-run `/dev-cycle #<N>` to continue.**
EOF
)"
```

### 8. Apply label

```bash
gh issue edit <N> --add-label "prd-pending" --remove-label "needs-po"
```

### 9. Halt

Tell the user: "PRD posted to issue #<N> and committed to `<prd_path>` on branch `<branch>`. Review it on GitHub and reply with approval or changes, then re-run `/dev-cycle #<N>`."
```

## Process

**Revision mode** — if the issue has `adr-pending`:
1. Find the last agent comment. Read all comments after it.
2. Apply the approval heuristic from `dev-workflow.md`.
3. If **approved**: transition `adr-pending` → `adr-approved` and halt: "ADR approved. Run `/engineer #<N>` (or `/dev-cycle #<N>`) to continue."

5. If **no response**: halt: "Waiting for your review of the ADR on issue #<N>."

**Fresh mode** — no `adr-pending` label: proceed to Step 5.

### 5. Read the PRD

```

### 6. Draft the ADR

# ADR: <issue title>

**Issue:** #<N>
**Date:** <today>
**Status:** Proposed

## Context

[The problem this decision addresses. Reference the PRD's Problem Statement. 2-4 sentences.]

## Alternatives Considered

### Option A: [name]
[Description. Pros and cons.]

### Option B: [name]
[Description. Pros and cons.]

### Option C: [name] *(chosen)*
[Description. Pros and cons.]

## Decision

[One clear paragraph stating the chosen approach and the primary reason it was selected over alternatives.]

## Consequences

**Positive:**
- [consequence]

**Negative / trade-offs:**
- [consequence]

## Implementation Notes

[Key constraints, interfaces, or patterns that engineers should follow. Describe WHAT is required, not HOW to implement it. No file paths.]
```

In revision mode: apply only the requested changes.

# Engineer

Implement a feature issue that has an approved ADR. Handles both initial implementation and revision cycles driven by code review.

## Invocation

```
/engineer #<issue-number>
```

The issue number can be the parent feature issue or a specific child issue.

## Process

### 1. Load workflow config

Read `docs/agents/dev-workflow.md`. If missing, halt and tell user to run `/dev-team-setup`.

### 2. Resolve to parent issue

If given a child issue number, fetch it and identify the parent:
```bash
gh issue view <N> --json body,title,labels
# look for "Parent: #<parent>" in the body
```

Fetch the parent issue to read its labels and docs.

### 3. Check preconditions

Parent issue must have `adr-approved` label. If it has `adr-pending` instead: "The ADR for #<parent> is awaiting your approval." Halt. If no ADR label at all: "Run `/tech-lead #<parent>` first." Halt.

### 4. Read the ADR

```bash
git checkout feature/<parent>-<slug>
cat docs/adr/<parent>-<slug>.md
```

Also read the PRD for broader context:
```bash
cat docs/prd/<parent>-<slug>.md
```

### 5. Check for child issues

Search for child issues linked to the parent:
```bash
gh issue list --search "\"Parent: #<parent>\"" --state open --json number,title,labels,body
```

**No child issues found (first run):**

Invoke `/to-issues` on the ADR content. This will present proposed vertical slices — approve them and let `/to-issues` publish them as child issues with `ready-for-agent` label. Apply `in-progress` to the parent issue:
```bash
gh issue edit <parent> --add-label "in-progress" --remove-label "adr-approved"
```

Then re-read the newly created child issues and proceed to Step 6 with the first unfinished one.

**Child issues exist:** Proceed to Step 6.

### 6. Select the current child issue

From the list of child issues, pick the first one that:
- Does NOT have label `done`
- Either has no open PR, or has an open PR with `changes-requested` review state

If all child issues are `done`, go to Step 9 (completion).

### 7. Check PR state

```bash
gh pr list --search "closes #<child>" --json number,reviewDecision,state
```

**No open PR:** proceed to Step 8 (implement).

**Open PR with `CHANGES_REQUESTED`:** proceed to revision mode.

**Revision mode:**
1. Read all open review comments on the PR:
   ```bash
   gh pr view <pr-number> --json reviews,comments
   ```
2. For each review comment: understand the issue and the file/line it references.
3. Implement the fixes. Commit each fix with a message that references the review comment:
   ```bash
   git commit -m "fix: address review comment — <brief description>"
   ```
4. Push and re-request review:
   ```bash
   git push
   gh pr review <pr-number> --comment --body "> *This was generated by AI during the dev team workflow.*

   Review comments addressed:
   - <comment 1 summary>: <what was done>
   - <comment 2 summary>: <what was done>

   Ready for re-review."
   ```
5. Halt after requesting re-review.

### 8. Implement the child issue

Read the child issue body carefully — it contains the vertical slice spec and acceptance criteria.

Implement the slice:
1. Explore the codebase to understand patterns, conventions, and the area being changed.
2. Write tests first (following existing test patterns in the repo).
3. Implement the code to make tests pass.
4. Commit with descriptive messages.

Open a draft PR:
```bash
gh pr create \
  --title "<child issue title>" \
  --body "$(cat <<'EOF'
> *This was generated by AI during the dev team workflow.*

Closes #<child>
Part of #<parent>

## What this does

[Brief description of the slice]

## How to test

[Testing instructions]
EOF
)" \
  --base feature/<parent>-<slug> \
  --draft
```

Apply `needs-review` label to the child issue:
```bash
gh issue edit <child> --add-label "needs-review"
```

Mark PR ready when done:
```bash
gh pr ready <pr-number>
```

### 9. Check for completion

If all child issues have `done` label:
1. All child PRs should already be merged into the feature branch.
2. Report: "All child issues are done. The feature branch `feature/<parent>-<slug>` is ready. Run `/dev-cycle #<parent>` to open the final PR or merge."
```

# Dev Review

Review an open PR on two axes: **Standards** (does the code follow this repo's conventions?) and **Spec** (does it implement what the PRD and ADR asked for?).

## Invocation

```
/dev-review #<issue-number>
```

The issue can be a child issue (with the PR) or a parent issue (will find the first open child PR).

## Process

### 1. Load workflow config

Read `docs/agents/dev-workflow.md`. If missing, halt and instruct user to run `/dev-team-setup`.

### 2. Find the PR

```bash
gh pr list --search "closes #<N>" --json number,title,headRefName,state
```

If no PR found, check the parent issue for open child PRs:
```bash
gh issue list --search "\"Parent: #<parent>\"" --state open --json number
# then check each child for a PR
```

If still no PR: "No open PR found for issue #<N>. Run `/engineer #<N>` first." Halt.

### 3. Read the spec

Identify parent issue and load:
```bash
cat docs/prd/<parent>-<slug>.md
cat docs/adr/<parent>-<slug>.md
```

### 4. Identify standards sources

Look for any of: `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md`, `CONTEXT.md`, `docs/adr/` (prior ADRs), `.eslintrc*`, `tsconfig.json`, `biome.json`. Collect the list.

### 5. Run two-axis review in parallel sub-agents

Dispatch two sub-agents simultaneously (in a single message with two Agent tool calls):

**Standards sub-agent brief:**
- Diff command: `git diff main...HEAD` (or the appropriate base)
- Standards files: [list from step 4]
- Task: "Read the standards docs. Read the diff. Report every place the diff violates a documented standard. Cite the standard (file + rule). Distinguish hard violations from judgment calls. Skip anything tooling already enforces. Under 400 words."

**Spec sub-agent brief:**
- Diff command: same
- Spec files: PRD path + ADR path

# Dev Cycle

One command to run (or resume) the full dev team workflow on a GitHub issue.

Invoke it after each GitHub approval to automatically advance to the next step.

## Invocation

```
/dev-cycle #<issue-number>
```

## How it works

`/dev-cycle` reads the issue's current label state and routes to the appropriate next action. It handles approval detection at the two HITL gates (PRD and ADR), driving the engineer-review loop until all child issues are done.

## State Machine

```
[no label / needs-po] → run /po → prd-pending → GATE: your PRD approval
prd-pending + approved → prd-approved → run /tech-lead → adr-pending → GATE: your ADR approval
adr-pending + approved → adr-approved → run /engineer → in-progress
in-progress → engineer-review loop → done
```

## Process

### 1. Load workflow config

Read `docs/agents/dev-workflow.md`. If missing, tell user to run `/dev-team-setup` first and halt.

### 2. Read current issue state

```bash
gh issue view <N> --json number,title,labels,comments
```

Extract the current state label.

### 3. Route by state

**No label, or `needs-po`:**
→ Run the `/po` skill for this issue. Halt after `/po` completes (it posts PRD and halts).

**`prd-pending`:**
→ Read comments after the last agent comment. Apply approval heuristic from `dev-workflow.md`.
- Approved: `gh issue edit <N> --add-label "prd-approved" --remove-label "prd-pending"`. Then run `/tech-lead` for this issue. Halt after `/tech-lead` completes.
- Revision requested: run `/po` for this issue (it will detect revision mode and update the PRD). Halt.
- No response: halt with: "Waiting for your PRD review on issue #<N>. Approve or request changes there, then re-run `/dev-cycle #<N>`."

**`prd-approved`:**
→ Run `/tech-lead` for this issue directly. Halt after it completes.

**`adr-pending`:**
→ Read comments after the last agent comment. Apply approval heuristic.
- Approved: `gh issue edit <N> --add-label "adr-approved" --remove-label "adr-pending"`. Then run `/engineer` for this issue.
- Revision requested: run `/tech-lead` for this issue (revision mode). Halt.
- No response: halt with: "Waiting for your ADR review on issue #<N>."

**`adr-approved`:**
→ Run `/engineer` for this issue. Halt after it opens the first draft PR.

**`in-progress`:**
→ Run the engineer-review loop (see below).

**`done`:**
→ Tell the user: "Issue #<N> is already complete." Halt.

### 4. Engineer-review loop

When the issue is `in-progress`:

1. List all child issues:
   ```bash
   gh issue list --search "\"Parent: #<N>\"" --state open --json number,title,labels
   ```

2. For each child issue without `done` label:
   a. Check if it has an open PR with `CHANGES_REQUESTED` — if so, run `/engineer #<child>`.
   b. Check if it has an open PR with no review yet — if so, run `/dev-review #<child>`.
   c. Check if it has no PR — run `/engineer #<child>`.
   d. After each action, re-read the child's state. If review was approved, move to the next child.

3. Loop until all child issues have `done` label.

4. When all child issues done:
   ```bash
   gh issue edit <N> --add-label "done" --remove-label "in-progress"
   ```
   Tell the user: "Feature complete! All child issues for #<N> are done. The feature branch `feature/<N>-<slug>` is ready to merge into main. Review the final PR or merge manually."

### 5. Skill composition note

`/dev-cycle` does not directly implement PO, Tech Lead, Engineer, or Review logic — it delegates to the respective skills. When invoking a sub-skill, load and follow it as if the user had typed it directly.
